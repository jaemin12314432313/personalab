# AI·데이터 팀에 부탁하는 일: UX 평가의 품질을 믿을 수 있게 만들기

작성: 2026-11-10 · 대상: PersonaLab을 처음 보는 AI·데이터 담당자 · 상태: 요청서 (결과 검증은 아직 없음)

## 한 줄 요약

PersonaLab은 AI 페르소나가 웹/HTML 화면을 실제 브라우저로 탐색하고, 화면·행동 근거가 붙은 UI·UX 평가를 리포트로 만든다. **파이프라인은 끝까지 돈다. 그러나 "그 평가가 얼마나 믿을 만한가"는 한 번도 측정하지 못했다.** 그 측정과, 측정 결과로 프롬프트·평가 형식을 다듬는 일을 부탁한다.

## 1. 지금 무엇이 있나

한 번의 실행: 페르소나 카드(약 400자) + 과제 + 현재 화면(요소 목록, 캡처 이미지) + 지나온 이력 → LLM이 다음 행동 하나와 평가를 JSON으로 답한다. 이것을 화면마다 반복한다.

모델이 한 단계에서 돌려주는 값 (`backend/app/services/browser.py`의 `decide_browser`):

| 필드 | 의미 |
| --- | --- |
| `action`, `target`, `value` | click / fill / scroll / abandon, 대상 요소 id |
| `drop_reason` | abandon일 때 이탈 사유 8개 중 하나. **8개는 변경 금지** (실제 참가자·앱 리뷰 라벨과 같은 축) |
| `reason` | 행동 이유 한 문단 |
| `observations` (최대 3개) | `dimension`(이해·길찾기·시각·입력·피드백·신뢰·조작성·인상), `polarity`(issue/good), `severity`(minor/moderate/blocking, good이면 null), `note` |

`blocking`은 "이 사람이라면 여기서 그만둘 만한 수준"이다. 페르소나가 실제로 그만두지 않아도 이탈 위험을 알려 주기 위한 값이다.

관련 위치: 프롬프트·검증 `backend/app/services/browser.py`, 인터뷰 `backend/app/services/interview.py`, 리포트 집계 `frontend/src/mockup/ReportModel.ts`, 상수·`PROMPT_REVISION` `backend/app/core/config.py`.
실행마다 `workflow.source_json.run_meta[run_id]`에 엔진·모델·`PROMPT_REVISION`·호출 수·토큰이 남는다.

## 2. 지금까지 측정한 것 (3명 × 최대 5턴, gpt-5.4-mini, 샘플 사이트 6페이지)

| 항목 | 값 |
| --- | --- |
| 호출 / 입력 토큰 / 출력 토큰 | 15회 / 약 4.5만 / 약 3.5천 |
| 호출당 입력 | 약 2,900토큰 (캡처 이미지 포함, 이력이 쌓일수록 증가) |
| 소요 시간 | 19초 (3명 동시) |
| 형식 위반 | 0건 (JSON 스키마 준수) |
| 이탈(abandon) | 0건. 세 명 모두 5턴을 끝까지 채움 |
| 사람마다의 경로 | 세 명(21세·디지털 높음 / 33세·디지털 낮음·개인정보 높음 / 79세)이 **같은 경로** |
| 단계당 관찰 수 | **항상 3개**(상한까지 채움) |
| 심각도 | `blocking` 0건, `moderate` 8건, `minor` 16건 |

관찰 예: "요금 안내 화면인데 요금이나 플랜 비교가 없다"(타당), "가입 완료하기가 링크 형태라 제출 방식이 애매하다"(타당), "여백이 넓어 허전하다"(모든 페이지에 반복), "화면이 단순해 이해하기 쉽다"(너무 일반적).
그중 하나는 의미 있는 확인이었다. 제품 소개가 "일정 관리 앱"인데 사이트가 책 기록 서비스라서, 모델이 "과제 맥락과 서비스 설명이 맞지 않는다"고 짚었다(제품 소개가 프롬프트에 들어간다는 증거).

## 3. 부탁하는 일 (중요한 순서)

### A. 정답이 있는 평가 세트 만들기 (가장 중요)
지금은 "찾은 문제가 맞는지, 놓친 문제가 얼마나 되는지" 알 방법이 없다.
- UX 문제를 사람이 미리 확인해 둔 화면 묶음 + 문제가 없는 정상 화면 묶음. 처음에는 5~10개 사이트/흐름이면 된다.
- 측정할 것: 재현되는 문제를 얼마나 찾았나(재현율), 정상 화면을 문제라고 한 비율(오탐), 중요한 문제를 놓친 정도.
- 완료 기준: 현재 프롬프트로 위 세 수치를 처음 한 번 잰다. 이후 프롬프트를 바꿀 때마다 같은 세트로 비교한다.

### B. 기준선과 비교: 페르소나가 정말 더 찾는가
- (1) 일반 AI에게 같은 화면을 한 번 검토시킨 결과, (2) 페르소나 카드만 바꾼 실행, (3) 수정 없이 같은 조건을 여러 번 돌린 결과를 비교한다.
- 핵심 질문: "같은 화면을 일반 AI 한 번에 보게 하는 것보다 무엇을 더 유용하게 찾는가?" 이 답이 없으면 인물 사진·대화가 신뢰만 부풀릴 수 있다.
- 오늘 시험에서 세 페르소나가 같은 경로를 간 것은 카드의 차이가 행동 차이로 이어지는지 의심하게 만든다.

### C. 반복 실행의 흔들림 측정
- 수정 없이 같은 조건으로 N번 돌려, 문제 수·심각도·경로가 얼마나 달라지는지 잰다.
- 용도: 회차 비교(▲▼)에서 "오차 범위"를 정한다. 지금은 임시로 `max(2, 인원의 10%)`명 미만 차이를 오차로 본다. 근거 없는 값이니 측정으로 대체해 달라.

### D. 프롬프트 개선 (A·C의 측정으로 효과 확인)
현재 알려진 약점:
1. 모델이 남은 턴 수를 모르고, "불편하면 그만둬도 된다"는 허락이 약하다. 이탈 0건.
2. `reason`이 "관찰한 사실: … 판단: …" 말투여서 리포트 인용문으로 어색하다. 그 사람의 1인칭 말이어야 한다.
3. 관찰이 항상 3개로 포화된다. "의미 있는 것만, 없으면 빈 배열"로 바꾸는 방법을 시험해 달라.
4. `blocking`을 한 번도 쓰지 않는다. 기준이 모델에게 와닿지 않는 것일 수 있다.
5. 페르소나 성향(디지털 친숙도, 개인정보 우려 등)이 카드 문장에 묻혀 행동에 반영이 약하다.

프롬프트를 바꾸면 `PROMPT_REVISION`을 올려야 한다. 회차 비교가 "같은 조건인지" 판단하는 근거다.

### E. 차원·심각도 분류 검증
- 7개 차원(이해·길찾기·시각·입력·피드백·신뢰·조작성·인상)이 적절한가. 겹치거나 빠진 것이 있나.
- 시각·인상은 모델이 캡처를 보고 하는 판단이라 신뢰가 낮다. 리포트에 "AI 인상 · 확인 필요"로 표시 중이다. 이 판단이 실제 사람의 평가와 얼마나 맞는지 알려 달라.
- 조작성·접근성 일부(터치 영역 크기, 입력칸 라벨, 제목 구조, 이미지 대체 텍스트)는 LLM 없이 DOM으로 직접 잴 수 있다. 어디까지 자동 점검으로 대체할지 의견을 달라.

### F. 인터뷰 답변의 근거 검증
- 지금은 모델이 인용한 로그 ID가 실제로 존재하는지만 확인한다. 그 로그가 답변의 주장까지 뒷받침하는지는 검증하지 않는다.
- 인터뷰는 "당시 이유"가 아니라 사후 설명이다. 행동 당시 기록과 모순되는 답이 나오는지 시험해 달라.

## 4. 지켜야 할 제약

- 이탈 사유 8개 코드(`UNCLEAR_PURPOSE`, `TOO_MANY_STEPS`, `PRIVACY`, `PRICE`, `TRUST`, `FEATURE_MISSING`, `SWITCHING_COST`, `NAVIGATION_LOST`)와 DB 스키마는 바꾸지 않는다. 새 분류는 observations 층에 얹는다.
- 결과는 "실제 사람의 응답"이 아니다. 시간·시선·감정 점수는 만들지 않는다.
- 비용: 30명 × 12턴이면 입력 100만 토큰 안팎으로 추정한다(호출당 약 2,900토큰 기준). 사용자별 한도는 아직 없고 정책을 정하는 중이다.
- 외부 전송: LLM 모드에서 페르소나 카드와 화면 캡처가 OpenAI로 전송된다. 실행 전 확인 체크가 있다.
- 평가 데이터에 실제 고객 정보를 쓰지 않는다.

## 5. 팀이 가져가면 좋은 것 / 질문

- 위 A·B에 필요한 사이트·화면 후보를 팀이 가진 것이 있는가.
- 평가에 쓸 "사람 정답"을 만들 수 있는가(UX 담당자의 판정 등).
- 모델 선택(현재 `gpt-5.4-mini`)이 이 용도에 적절한가. 이미지 입력 해상도와 비용의 균형은?
- 같은 입력에 대한 흔들림을 줄일 방법(온도, 반복 후 합의 등)이 있는가.

## 6. 재현 방법

- 백엔드 설정은 `.env`의 `AGENT_ENGINE`(`rule`/`llm`/`auto`). 기본은 `rule`(AI 호출 없음, 비용 0, 체험용).
- LLM 시험은 소규모(3명 × 5턴, 호출 약 15회)로 하면 입력 약 4.5만 토큰이 든다.
- 실행 결과는 `GET /runs/{run_id}/report`의 `results[].act.events[].observations`와 `meta`(엔진·모델·프롬프트 개정·사용량)에서 읽는다.
