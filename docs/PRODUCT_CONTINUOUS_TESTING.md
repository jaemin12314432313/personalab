# PersonaLab — 한 제품을 여러 방향으로 계속 검토하는 구조

작성: 2026-11-07 · 사용자 방향 수정 반영  
연결: [주 구성 기획](PRODUCT_MASTER_PLAN.md) · [화면 명세](PRODUCT_SCREEN_SPEC.md) · [아이디어 백로그](PRODUCT_IDEA_BACKLOG.md)

> **PersonaLab은 하나의 앱·웹 제품을 등록하고, 여러 UI·UX 테스트를 쌓으며, 제품이 바뀔 때 필요한 테스트를 다시 실행해 근거와 변화를 관리하는 공간이다.**

이 문서는 이전 ‘내 테스트 중심 홈, 제품 계층은 나중’ 권장안을 대체한다. 사용자가 제품 중심 사용을 확정했으므로 제품은 기본 작업 맥락이다. 기존 3D 관찰·리포트·인터뷰는 그 안의 각 실행에 연결한다. 아래 내용은 제품 기획이며 앱·DB에 구현됐다는 뜻은 아니다.

## 1. 조사한 사례와 우리가 취할 구조

| 사례 | 공식 자료에서 확인한 것 | PersonaLab에 적용할 점 |
| --- | --- | --- |
| [Maze 프로젝트](https://help.maze.co/articles/8568957568-creating-a-project) | 프로젝트에 여러 연구를 넣고 초안·진행 연구를 모아봄 | 한 앱의 가입·검색·결제 등을 하나의 제품 공간에 모음 |
| [Maze 연구 복제](https://help.maze.co/articles/1972110399-how-to-duplicate-a-study) | 설정을 복사한 새 초안을 만들며 기존 결과는 복사하지 않음 | 같은 조건을 재사용하되 새 실행 결과는 독립 보존 |
| [Lyssna 프로젝트](https://help.lyssna.com/en/articles/4952934-creating-projects) | 테스트·인터뷰를 프로젝트로 정리하고 나중에 이동 가능 | 개별 결과가 제품 맥락을 잃지 않게 연결 |
| [Useberry 구조](https://useberry.zendesk.com/hc/en-us/articles/36702114336669-Useberry-Projects-types) | Workspace → Project → Versions 계층, 같은 연구의 변형·반복을 지원 | 목적을 유지한 재검토의 이력을 명확히 구분 |

공식 사례의 프로젝트가 곧 우리 앱 제품과 같은 데이터 모델이라는 뜻은 아니다. **여러 연구를 묶는 단위와 반복 결과를 보존하는 단위를 분리한다**는 구조를 참고한 것이다. 아래의 제품 버전·공통 화면 재사용·선택 재실행은 우리 사용 목적에 맞춘 제안이며 사례들이 모두 같은 기능을 제공한다고 주장하지 않는다.

## 2. 고객이 보게 될 기본 구조

```text
워크스페이스
└─ 제품: 일정메이트
   ├─ 공통 자료
   │  ├─ 연결: 웹 / iOS 프로토타입 / Android 프로토타입
   │  ├─ 화면 버전: 초기 화면 / 가입 수정본 / v1.4
   │  └─ 저장한 대상 사용자·참여 구성
   ├─ 테스트: 전반 탐색
   │  ├─ 1회차: 초기 화면 · 5명
   │  └─ 2회차: v1.4 · 같은 구성
   ├─ 테스트: 가입과 첫 일정 등록
   │  ├─ 1회차: v1.3 · 처음 사용하는 사람 5명
   │  └─ 2회차: v1.4 · 같은 조건
   ├─ 테스트: 검색과 일정 찾기
   ├─ 테스트: 예약 변경
   ├─ 발견 모음: 여러 테스트에서 나온 문제와 근거
   └─ 실행 기록: 회차별 관찰·리포트·해당 페르소나 인터뷰
```

**사용자는 매번 새 제품을 연결하는 것이 아니라, 같은 제품 안에서 검토할 관점을 추가하거나 이전 검토를 다시 실행한다.**

화면에서 제품명은 실제 서비스명으로 쓴다. 관리 화면의 묶음 이름은 ‘내 앱·웹’ 또는 ‘내 제품’이 적절하다. ‘프로젝트’라는 추가 이름을 제품 위에 또 만들지는 않는다.

### 네 가지 단위를 구분

| 단위 | 의미 | 예시 | 바뀔 때의 처리 |
| --- | --- | --- | --- |
| 제품 | 계속 개선할 하나의 앱·웹 서비스 | 일정메이트 | 제품 내부에서 여러 테스트 관리 |
| 테스트 | 반복해서 확인할 UX 질문·흐름·관점 | 가입과 첫 일정 등록 | 질문이 달라지면 다른 테스트 추가 |
| 화면 버전 | 특정 시점의 연결·수집 자료 | v1.3 / 가입 수정본 / 11월 7일 캡처 | 새 버전으로 저장하고 과거 자료 보존 |
| 회차·실행 | 특정 버전·환경·사람·범위로 수행한 검토 | 가입 테스트 3회차 | 새 결과·인터뷰를 독립 연결 |

고객에게 복잡한 계층 네 개를 모두 생성하라고 요구하지 않는다. 제품 등록 시 이름과 연결 자료를 받고 첫 화면 버전을 자동 제안한다. 테스트 실행 시 조건을 고정해 회차를 만든다. 기술적으로 실행 재시도가 여러 개면 이력 상세에서 확인하게 하되 최신 결과를 조용히 덮어쓰지 않는다.

### 무엇을 새로 만드는가

| 사용자의 의도 | 해야 할 동작 |
| --- | --- |
| 다른 앱을 살펴본다 | 제품 등록 |
| 같은 앱에서 다른 흐름·질문을 본다 | 제품 안에 테스트 추가 |
| 같은 앱·같은 질문, 화면을 수정했다 | 새 화면 버전으로 같은 테스트 재검토 |
| 같은 화면을 다른 사용자 관점으로 본다 | 같은 테스트의 조건을 바꾼 회차. 반복 사용할 관점이면 별도 테스트로 저장 가능 |
| 일시 오류로 끝나 다시 시도한다 | 같은 입력 스냅샷의 재시도 이력. 비용·이전 기록을 보존 |
| 결과의 이유를 더 묻는다 | 해당 회차·해당 페르소나 인터뷰 |
| 앱의 웹과 모바일을 본다 | 같은 제품의 환경별 실행. 초기 비교에서는 다른 조건임을 표시 |

## 3. 로그인 후 홈을 두 수준으로 구성

### 제품을 여러 개 관리할 때: 내 제품

상단 ‘내 앱·웹’과 ‘제품 등록’. 본문은 제품 카드 또는 간결한 목록이다.

제품 카드 필수 정보:

- 제품명·아이콘·자료 종류.
- 최근에 확인한 화면 버전.
- 실행 중인 테스트, 결과를 볼 테스트, 최신 버전에서 아직 안 본 테스트의 요약.
- 마지막 작업 한 줄과 ‘이어서 보기’.
- 더보기: 이름 변경·보관·휴지통.

제품 상태를 ‘완료’ 하나로 표시하지 않는다. 같은 앱에는 완료한 테스트와 아직 안 본 테스트가 함께 있기 때문이다. 요약 개수는 실제 상태가 있는 경우에만 표시한다.

### 하나의 제품을 주로 쓸 때: 바로 제품 홈

로그인하면 마지막으로 사용한 제품 홈으로 복원한다. 제품이 하나면 불필요한 선택 화면을 매번 거치지 않는다. 왼쪽 위 제품 선택기에서 다른 제품과 전체 제품 목록에 접근한다. 진행 중인 작업의 직접 링크는 그 위치를 유지한다.

제품이 없을 때만 첫 제품 등록을 안내한다. 프로젝트 설정·팀 만들기·폴더 생성은 필수 온보딩 단계로 추가하지 않는다.

## 4. 제품 홈의 구체적인 배치

```text
┌ 제품 사이드바 ────────┬────────────────────────────────────────────────┐
│ PersonaLab           │ 일정메이트                 [화면 업데이트]     │
│ 일정메이트 ▾         │ 현재 자료: v1.4 · 웹 / 모바일 프로토타입        │
│                      │                                                │
│ ● 테스트             │ 진행 중: 가입 2회차 · 5명 중 2명 종료 [보기]    │
│   발견 모음           │ ── 실행 중일 때만 한 줄 ───────────────────── │
│   실행 기록           │ [검색] [전체 / 진행 중 / 재확인 필요] [+ 테스트]│
│                      │                                                │
│ 공통 자료·참여 구성 ↗│ 테스트              최근 결과           다음 행동 │
│                      │ 전반 탐색        v1.3 · 1회차   [v1.4로 재검토]│
│                      │ 가입·첫 일정     v1.4 · 실행 중      [관찰]    │
│                      │ 검색·일정 찾기   v1.3 · 2개 발견 [v1.4로 재검토]│
│                      │ 예약 변경        작성 중           [이어서 설정]│
│                      │                                                │
│ 계정                 │ [선택한 테스트 2개]              [실행 준비]    │
└──────────────────────┴────────────────────────────────────────────────┘
```

기본 탭은 ‘테스트’다. 제품 홈과 동일 내용을 가진 ‘개요’ 탭을 다시 만들지 않는다. 발견 모음은 근거를 제품 단위로 묶는 별도 역할, 실행 기록은 과거 작업을 찾는 역할이다. 초기에는 발견 모음의 저장·묶기 기능이 검증되기 전 장식용 메뉴로 먼저 노출하지 않는다.

### 첫 화면에서 가장 먼저 답할 네 질문

1. 지금 어떤 앱·어떤 화면 버전을 보고 있나?
2. 실행 중인 것이 있나?
3. 어떤 검토를 했고 현재 버전에는 무엇이 남았나?
4. 이전 테스트를 이어서 보거나 다시 돌리려면 어디를 누르나?

차트·캘린더·거대한 인사말보다 이 네 질문이 먼저다. 기본 목록에는 테스트 5~8개 내외를 시작점으로 검토하고 검색·페이지 이동을 제공한다. 모든 회차를 홈에 개별 카드로 펼치지 않는다.

### 테스트 행에 들어갈 것

테스트명, 확인 관점/흐름, 마지막 실행의 화면 버전, 최신 회차, 진행·종료 상태, 근거 있는 한 줄 요약, 다음 버튼 하나. 페르소나 전체 명단·전체 이력·긴 총평은 상세에서 연다.

| 현재 상황 | 버튼 | 보조 설명 |
| --- | --- | --- |
| 설정만 저장함 | 이어서 설정 | 공통 자료는 연결됨 / 참여 구성 필요 |
| 현재 실행 중 | 실행 보기 | 이번 실행이 고정한 버전·진행 인원 |
| 현재 버전에서 종료함 | 결과 보기 | 관련 발견 수 또는 관찰 요약 |
| 이전 버전에서만 실행함 | 최신 화면으로 재검토 | 마지막 검토: v1.3 / 현재 자료: v1.4 |
| 중단·부분 기록 | 부분 기록 보기 | 저장 범위·누락 인원 |
| 테스트는 만들었으나 실행한 적 없음 | 실행 준비 | 실행 전 조건 확인 |

‘최신 화면으로 재검토’는 버튼 클릭 즉시 과금 실행하지 않는다. 어떤 버전·조건으로 돌릴지 짧게 확인하고 실행한다.

## 5. 공통 자료를 한 번 연결하고 재사용

### 제품에 저장할 공통 정보

| 공통 정보 | 재사용 방식 | 덮어쓰지 않을 것 |
| --- | --- | --- |
| 이름·소개 | 새 테스트의 기본 문맥 | 기존 실행 당시의 입력 |
| 연결 자료·환경 | 웹/프로토타입 주소와 화면 크기 선택 | 과거 URL/캡처/환경 |
| 수집한 화면 버전 | 새 테스트가 사용할 자료 묶음 선택 | 이전 회차의 화면 상태 |
| 대상 사용자 설명 | 새 테스트에 기본값 제안 | 해당 테스트에서 수정한 설명 |
| 저장 참여 구성 | 조건/사람을 다시 선택하는 수고 감소 | 이미 종료한 실행의 참여자 |
| 자주 쓰는 테스트 | 목적·범위·확인 기준 재사용 | 이전 결과와 인터뷰 |

새 테스트마다 앱 이름·제품 소개·주소를 다시 묻지 않는다. 공통 자료를 상속한 뒤 필요한 부분만 바꾸게 한다.

### 화면 업데이트

제품 홈 ‘화면 업데이트’ → 기존 연결을 다시 확인하거나 새 자료 업로드 → 수집 결과 확인 → 새 자료 버전 저장. 버전 이름은 선택이며 ‘11월 7일 화면’처럼 자동 제안할 수 있다. 사용자가 배포 버전을 모르면 억지로 v1.0을 쓰게 하지 않는다.

새 버전 저장 후 선택:

- ‘이 버전으로 검토할 테스트 선택’.
- ‘나중에 검토’.

화면 업데이트가 이미 끝난 리포트·실행 중 브라우저·열려 있는 인터뷰의 자료를 바꾸면 안 된다. 실행은 시작 시 고정한 자료를 사용한다. 업데이트된 화면이 있다고 해서 이전 결과가 틀렸다는 뜻도 아니다. **다른 버전에 대한 과거 결과**로 보존한다.

웹의 같은 URL이 나중에 바뀔 수 있으므로 버전명만으로 재현을 보장하지 않는다. 실제 관찰 시각·캡처·접근 환경을 함께 남긴다. 원본 웹의 배포 상태를 고정하지 못하는 경우 그 한계도 표시한다.

## 6. 한 앱에서 만들 다양한 테스트

처음에는 ‘전반 탐색’ 초안을 제안하고 사용자가 설정을 확인하게 한다. 실제 실행은 별도 시작 버튼을 누른 후다. 모든 템플릿을 자동 생성하거나 실행하지 않는다.

| 테스트 예시 | 확인할 UI·UX | 설정 부담 |
| --- | --- | --- |
| 전반 탐색 | 시작 화면 이해·메뉴 발견·주요 경로·안내 | 기본값. 특정 과제 필수 아님 |
| 첫 사용·온보딩 | 시작하기·가입·첫 핵심 행동 | 실제 시작/완료 지점 선택 |
| 기능 발견·탐색 | 원하는 메뉴와 기능을 찾는 과정 | 관심 기능 선택 |
| 검색·필터 | 검색 입력·결과·필터 상태·빈 결과 안내 | 관련 화면과 가능 입력 |
| 입력·수정 | 폼 이해·검증·수정·취소/뒤로 이동 | 테스트 환경과 변경 동작 제한 |
| 예약·결제 전 흐름 | 옵션·비용/상태 안내·확인 과정 | 실제 구매·결제와 구분, 보호 유지 |
| 계정·설정 | 내 정보·설정·상태/저장 안내 발견 | 로그인 자료 지원 여부 |
| 오류·복구 | 실패·빈 상태·복구 안내를 이해하는지 | 해당 상태를 실제로 만들거나 자료 제공 |
| 특정 관점 | 친숙도·사용 상황이 다른 구성의 탐색 | 실제 데이터로 지원하는 조건 |
| 수정 후 재확인 | 이전 문제가 새 화면에서도 관찰되는지 | 같은 테스트·가능한 같은 조건 |

‘전체’는 지원 범위 안에서 여러 방향으로 살펴보는 모드다. 집중 테스트를 추가해도 기존 전반 탐색 결과를 대신하지 않는다. 구매 의향·시장성·가격 설문은 이 목록에 포함하지 않는다.

### 테스트 추가 창

제품 홈에서 ‘테스트 추가’ → 이름과 방식 선택(전반 탐색 / 특정 흐름 / 저장한 테스트 재사용) → 공통 화면·대상·구성 제안 → 필요한 범위만 수정 → 실행 확인.

기존 여섯 설정 페이지는 세부 편집으로 재사용한다. 이미 확인된 공통 자료는 요약 상태로 들어오고, 변경된 화면 버전·저장 안 된 조건만 다시 확인한다. ‘단계를 짧게 한다’며 확인되지 않은 연결·누락 자료를 건너뛰지는 않는다.

## 7. 반복 실행을 제품의 핵심 행동으로 만들기

### 사용자가 가장 많이 반복할 장면

1. 전반 탐색에서 가입 화면의 안내 문제가 관찰됨.
2. ‘가입·첫 일정’ 집중 테스트를 만들어 구체적인 경로 확인.
3. 리포트에서 해당 장면을 열고 같은 페르소나와 인터뷰.
4. 사용자가 제품을 수정하고 새 화면 버전을 연결.
5. 제품 홈에서 가입 테스트만 선택해 같은 조건으로 재검토.
6. 이전 문제의 재관찰 여부와 새로 생긴 관찰을 비교.
7. 필요할 때 검색·예약 등 다른 테스트를 추가/재실행.

고객이 반복할 때 앱 이름·소개·참여 조건을 다시 입력하지 않도록 한다. 결과가 제품에 쌓여야 다음에 무엇을 볼지도 쉽게 알 수 있다.

### 재검토 시 고정하거나 바꿀 조건

| 조건 | 기본 권장 | 바뀌었다면 |
| --- | --- | --- |
| UX 질문·범위 | 동일 유지 | 다른 질문이면 다른 테스트 제안 |
| 화면 자료 | 선택한 새 버전 | 어떤 자료로 바뀌었는지 표시 |
| 참여 구성 | 같은 구성 재사용 | 신규/변경 인원과 사유 표시 |
| 기기·화면 크기 | 동일 유지 | 다른 조건 비교라고 표시 |
| 행동/시간 상한 | 동일 유지 | 한도 변화가 결과에 미칠 영향 표시 |
| 모델·엔진 설정 | 기록해 비교 시 확인 | 차이가 있으면 단순 개선 판정 제한 |
| 세션·대화 기억 | 새로운 탐색은 새 브라우저/새 문맥으로 시작 | 이전 경험을 기억시키는 장기 실험은 별도 설계 |

같은 페르소나를 재사용한다는 것은 프로필 조건을 유지한다는 뜻이다. 이전 인터뷰 전체를 새 탐색에 자동 주입해 수정된 정답을 아는 참가자로 만들지 않는다. 확률적 변동 때문에 같은 조건도 완전히 같은 결과를 보장하지 않는다.

### 비교 화면의 기본 표기

‘가입·첫 일정 / 1회차(v1.3) ↔ 2회차(v1.4)’로 표시한다. **앱 버전과 테스트 회차는 서로 다른 값**이다. 앱 v1.4 안에서도 조건을 바꿔 여러 회차를 돌릴 수 있다.

새 실행에서 같은 화면을 방문하지 않았다면 해결이 아니라 미관찰/비교 불가다. 사람·과제·자료가 달라졌으면 변화를 명시한다. 전반 탐색과 특정 과제의 성공률을 같은 지표로 비교하지 않는다.

## 8. 선택한 테스트 여러 개를 다시 돌리기

여러 방향을 관리하는 서비스에서는 테스트마다 따로 같은 설정을 반복하는 부담도 줄여야 한다.

권장 흐름: 제품 홈에서 체크 → ‘선택한 테스트 실행 준비’ → 사용 화면 버전·각 테스트 참여 구성·전체 상한 요약 → 시작.

- 첫 구현은 테스트 하나씩의 재실행을 안정화한다.
- 다음 단계에서 선택 묶음 실행과 작업 큐를 붙인다. 병렬로 모두 시작하는 것을 기본값으로 삼지 않는다.
- 테스트별 대기/실행/완료/부분/실패를 따로 보여준다. 하나가 끝났다고 전체 묶음 완료로 표시하지 않는다.
- 실행 버튼 중복·새로고침으로 같은 작업을 두 번 만들지 않는다.
- 사람 수 × 테스트 수 × 행동 상한으로 전체 규모를 보여주되 실제 금액은 검증된 비용 산정이 있어야 한다.
- 화면 업데이트만으로 자동 유료 실행하지 않는다.
- 조건 3개 × 기기 2개 × 테스트 5개를 자동으로 전부 실행하는 방식은 피한다. 선택한 조합만 실행한다.
- ‘완료한 테스트 제외·실패한 테스트만 재시도’는 새 이력을 만들고 기존 결과를 보존한다.
- 정기/배포 연동 자동 실행은 예산·알림·인증·중단 정책을 갖춘 뒤 별도 기능으로 검토한다.

## 9. 제품 단위로 쌓일 결과

개별 리포트는 그대로 유지하고 제품에 결과의 색인을 만든다.

### 제품의 발견 모음

| 내용 | 처리 원칙 |
| --- | --- |
| 가입 관련 발견이 여러 테스트에서 나옴 | 관련 근거를 모으되 같은 사람/같은 기록 중복 집계 금지 |
| 과거 버전의 발견 | 버전·회차 표시. 최신 앱의 현재 문제처럼 표시하지 않음 |
| 수정 후 같은 문제가 다시 관찰됨 | 재관찰된 기록 연결 |
| 이번에 관찰되지 않음 | 미관찰과 해결 확인을 구분 |
| 사용자가 수정했다고 표시함 | 사용자 작업 상태와 AI의 새 관찰을 별도 표기 |
| 서로 다른 테스트에서 표현이 다름 | 같은 문제 묶기 제안, 원본 근거는 보존 |

제품의 종합 UX 점수 하나를 만들기보다 **현재 버전에서 어떤 테스트를 했고 어떤 근거가 남았는지**를 보여준다.

### 최신 버전의 검토 현황

행은 저장한 테스트, 열은 마지막 검토 버전·실행 상태·발견·다음 행동이다. 필요할 때 기기/참여 구성별 보기로 확장하되 홈에서 거대한 행렬을 기본 출력하지 않는다.

‘전반 탐색 v1.3만 확인’, ‘가입 v1.4 부분 기록’, ‘검색 v1.4 미실행’처럼 표시한다. 3개 테스트 중 2개 실행했다고 앱의 67%를 검증했다고 쓰지 않는다.

## 10. 내비게이션과 버튼 문구 변경

| 위치 | 주 행동 | 맥락 |
| --- | --- | --- |
| 제품이 없는 첫 화면 | 앱·웹 등록 | 처음 한 번 제품과 자료 연결 |
| 전체 제품 목록 | 제품 등록 | 다른 앱을 추가할 때 |
| 제품 홈 | 테스트 추가 / 화면 업데이트 | 같은 앱에서 검토 관점 추가·자료 갱신 |
| 저장한 테스트 행 | 실행 보기 / 결과 보기 / 최신 화면으로 재검토 | 상태에 맞게 하나를 강조 |
| 테스트 결과 | 같은 조건으로 다시 검토 | 새 자료 선택·조건 확인 후 실행 |
| 여러 테스트 선택 | 선택한 테스트 실행 준비 | 전체 범위·상한 확인 |
| 테스트 내부 로고 | 현재 제품 홈 | 앱 맥락으로 돌아가기 |
| 제품 선택기의 전체 보기 | 전체 제품 | 앱을 바꾸거나 관리 |

이전의 ‘내부 로고는 내 테스트 목록으로’는 제품 구조 도입 후 **현재 제품 홈으로** 바꾼다. 공개 로고는 랜딩이다. 제품이 없거나 접근 권한이 없어졌으면 전체 제품 목록으로 복구한다.

제품 안에서는 테스트 목록·발견 모음·실행 기록이 제품 범위다. 전역 기록이 필요하면 제품 필터를 명시한다. 제품 이름만 바꾼 채 다른 제품의 기록이 남아 있으면 안 된다.

## 11. 기존 데이터와 연결할 때의 조건

현재 코드를 확인하면 `products`의 `Product`는 `study_id`에 속한 입력이며, 여러 독립 테스트를 소유한 제품 허브는 아니다. `study_workflows.root_study_id`는 같은 테스트의 회차 묶음을 나타낸다.

따라서 다음을 구분해야 한다.

1. 기존 테스트·회차·실행·관찰·인터뷰는 보존한다.
2. 새 제품 묶음과 기존 테스트 묶음의 관계를 명시적으로 설계한다. 기존 `root_study_id`를 제품 ID로 재해석하지 않는다.
3. 앱 이름이나 URL이 같다고 자동 병합하지 않는다. 다른 앱일 수 있고 같은 앱의 다른 환경일 수도 있다.
4. 기존 사용자는 ‘기존 테스트를 제품에 연결’하는 선택을 제공한다. 잘못 옮겼을 때 소속을 복구할 수 있어야 한다.
5. 자료와 참여 구성은 기본값 재사용이며 과거 실행에 대한 일괄 갱신이 아니다.
6. 공통 자료·화면 버전·제품별 권한·삭제/이동 범위의 저장 계약을 먼저 정의한다.
7. 현재 DB 변경 금지 규칙에 따라 기술 명세·마이그레이션 검토 없이 테이블/컬럼을 추가하지 않는다. 이번 작업에서는 변경하지 않았다.
8. 제품 분류를 로컬스토리지에만 넣고 다른 PC에서도 서버 기능이 완성된 것처럼 보이게 하지 않는다.
9. 제품 삭제·테스트 이동이 하위 기록과 권한에 미치는 범위를 분명히 한다. 이동 때문에 과거 인터뷰가 다른 실행에 연결되지 않아야 한다.

## 12. 구현 순서

| 순서 | 범위 | 확인할 완료 기준 |
| --- | --- | --- |
| 1 | 제품과 테스트 소속 | 한 제품에 가입·검색 등 두 독립 테스트를 저장·새로고침·다른 세션에서 확인 |
| 2 | 제품 공통 자료 | 자료를 한 번 연결한 뒤 두 테스트가 재입력 없이 선택 사용 |
| 3 | 화면 버전·반복 실행 | 같은 테스트를 두 버전에서 검토하고 과거 캡처·조건·인터뷰 보존 |
| 4 | 제품 홈과 상태별 CTA | 현재 자료 기준 미실행/예전 결과/부분/진행 상태를 정확히 표시 |
| 5 | 제품 발견 색인·비교 | 서로 다른 테스트의 근거를 찾고 버전·조건에 맞게 해석 |
| 6 | 선택 묶음·작업 큐 | 두 테스트의 예산·진행·실패·취소가 개별/전체에서 일치 |
| 7 | 자동화 확장 | 배포/예약 트리거·비용 상한·중복 방지·알림을 별도 검증 |

실행 화면의 실제 캡처·행동 일치와 완료/부분 게이트는 이 구조를 만들면서도 지켜야 한다. 제품 허브가 생겼다고 엔진 안정성 검증이 생략되지는 않는다.

## 13. 실제 이용 예시로 검수

- 일정메이트 등록 → 첫 화면 한 번 수집 → 전반 탐색과 가입 테스트에 재사용.
- 가입 테스트와 검색 테스트의 대상·범위를 다르게 저장 → 같은 제품 홈에서 구분.
- 가입 v1.3 결과를 인터뷰까지 확인 → v1.4 연결 → 가입만 재실행.
- 가입은 v1.4, 검색은 v1.3인 상태를 홈에서 오해 없이 구분.
- 앱 자료 업데이트 중 기존 실행 진행 → 진행 중 실행과 이전 리포트가 바뀌지 않음.
- 같은 페르소나 재사용 → 새 브라우저/새 탐색 문맥, 과거 인터뷰는 과거 실행에 유지.
- 테스트 3개 선택 → 상한 확인 → 작업 큐 → 1개 실패해도 나머지 결과와 실패 범위 보존.
- 같은 URL을 쓰는 개발/운영 제품 → 이름·URL만으로 합쳐지지 않음.
- 기존 독립 테스트를 제품에 연결 → 소속 변경만 반영, 증거/리포트/인터뷰 보존.
- 제품 하나인 계정 → 로그인 후 제품 홈 직행. 제품 두 개 계정 → 마지막 제품 복원·선택 전환.

## 14. 이번 방향에서 먼저 추가할 아이디어

- **제품 공통 화면 라이브러리:** 연결·수집을 반복하는 부담 감소.
- **저장된 테스트 목록:** 전반·가입·검색·설정 등의 관점을 제품에 남김.
- **현재 버전에서 아직 안 본 테스트:** 새 화면을 올렸을 때 할 일을 바로 알려줌.
- **같은 조건으로 재검토:** 자료만 바꾼 실행을 짧은 확인으로 시작.
- **변경 부분에서 관련 테스트 제안:** 화면 연결·명시된 변경 메모를 근거로 제안하고 사용자가 선택. 자동 영향 분석 확정으로 표현하지 않음.
- **선택한 테스트 묶음 실행:** 충분한 예산 확인·작업 큐를 갖춘 후 제공.
- **제품의 발견 이력:** 과거/현재 버전과 사용자 수정 상태·새 관찰을 분리해 추적.

새 아이디어 I61~I80과 구체적인 위치·우선순위는 [아이디어 백로그](PRODUCT_IDEA_BACKLOG.md)에 추가한다.

## 15. 구현 현황 (2026-11-07)

이 문서의 방향을 **DB 스키마를 바꾸지 않는 범위**에서 먼저 적용했다. 아래는 구현된 것과 아직 아닌 것이다.

### 구현한 것
- **앱·웹(제품) 소속:** 테스트를 같은 앱·웹으로 묶는 `product_id`와 테스트 이름 `test_title`, 회차 상세 `round_note`를 워크플로 범위(`study_workflows.scope_json`, 자유 형식 JSONB)에 저장한다. 새 테이블·컬럼은 없다. `GET /studies`가 세 값을 함께 돌려준다. 기존 `root_study_id`를 제품 ID로 재해석하지 않았고, 이름·주소가 같다는 이유로 합치지도 않는다. 소속 정보가 없는 기존 테스트는 각각 독립 항목으로 보인다.
- **새 테스트 창:** 만든 앱·웹을 고르거나 새로 추가하고, "무엇을 살펴볼까요?"(테스트 이름, 새 앱·웹은 기본 "전반 탐색")를 정한다. 기존 앱·웹을 고르면 이전 연결 주소·화면 크기·대상 사용자·설명을 이어받는다(화면 연결은 다시 눌러 확인).
- **수정 회차:** 회차 상세만 받는다. 테스트 이름과 소속은 회차로 이어지고 회차 상세만 새로 적는다(백엔드 `POST /studies/{id}/revisions`의 `note`).
- **사이드바:** 앱·웹별로 묶어 보여 준다. 한 앱·웹에 테스트가 둘 이상일 때만 머리글을 둔다. 화면을 연결하지 않은 빈 초안은 "작성 중 · 화면 미연결"로 접는다(지우지 않음).
- **정리한 중복:** 캘린더·목록 탭, 개요와 같은 내용의 보조 화면, 사이드바의 3개 메뉴(내 테스트·페르소나 보관함·전체 실행 기록)를 걷고 전체 실행 기록은 하단 링크로 남겼다. 6단계 이름은 마지막을 "실행"으로 바꿨다.
- **저장:** 화면 연결만 해도 앱·웹 소속·테스트 이름·회차 상세가 서버에 남는다. 실행이 끝나거나 중단되면 결과 스냅샷(`run_reports`)을 저장한다.

### 아직 아닌 것 (백로그 기준)
- 제품 공통 화면 라이브러리와 화면 버전의 분리(I62·I65): 지금 "수정 회차"는 입력을 복사한 새 회차이며 화면 버전과 회차가 한 덩어리다.
- 선택한 테스트 묶음 실행과 작업 큐(I71), 버전별 검토 현황(I66·I73), 제품의 발견 이력(I74).
- 기존 소속 없는 테스트를 앱·웹에 연결하는 이동 기능(I69).
- 공유 링크·협업·자동화(I49~I54·I80).

### 에이전트 판단 엔진
모델 비용을 쓸 수 없는 환경을 위해 **규칙 기반 엔진**을 두었다(`AGENT_ENGINE=rule`, 기본 `auto`는 모델 키와 카드 전송 허용이 모두 있을 때만 모델 사용). 눌러 볼 요소를 과제 단어·행동 유도 문구·페르소나별 순서로 고르며 결제·삭제·탈퇴 같은 변경 동작은 누르지 않는다. 결과에는 "규칙 기반 탐색" 머리말이 붙고 리포트에 "체험용 기록, 실제 AI 페르소나 판단이 아님"이 표시된다. 이 모드에서는 인터뷰의 유료 질문(llm)이 막히고 기록 조회(records)만 된다. 규칙 기반이 만든 결과를 실제 UX 문제 발견으로 해석하지 않는다.
