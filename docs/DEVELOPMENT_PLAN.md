# PersonaLab 개발계획서

**AI 페르소나 기반 UI·UX 탐색과 후속 인터뷰 플랫폼**

3개월 / 12주 · 8인 · 팀 배포용

> 화면은 같아도, 경험은 다르니까.

## 2026년 11월 2일 제품 방향 변경

사용자 결정에 따라 기획 의견·사용 의향·기능 선호·지불 의향 조사를 제품 범위에서 제외한다. 기본 흐름은 **프로토타입 등록 → 페르소나 선택 → 전반 탐색 범위 확인과 선택적 집중 확인 → UI·UX 실행 → 근거 중심 결과 → 같은 페르소나와 1대1 인터뷰 → 수정 후 재실행**이다.

현재 제품 정의·화면 흐름·개발 순서·의문점과 해결안의 기준은 **[UI·UX 서비스 정의와 개발 기준](UX_WORKFLOW.md)**이다. 이 문서의 기존 1~5장, 7장, 일정과 로드맵 중 새 방향과 충돌하는 부분은 이전 구현을 이해하기 위한 참조로 둔다. 기존 Ask 코드·응답을 후속 인터뷰로 간주하지 않는다.

8장의 실행 종료 조건, 9장의 현재 DB 명세, 이탈 코드 8개는 유지한다. 보관함·다중 시나리오·인터뷰·사용량 원장은 새 문서의 설계 제안이며, 구현 시 이 계획서에 구체적인 스키마·API·이행 절차를 먼저 명시한다. 이번 정리에서 DB 변경과 신규 엔진 기능 구현을 완료한 것으로 처리하지 않는다.

## 0. 이 문서를 읽는 법

이 문서는 설득용이 아니라 **작업 지시서**다. 각자 자기 파트만 읽어도 무엇을 만들어야 하는지 알 수 있도록 썼다.

| 역할 | 반드시 읽을 장 |
| --- | --- |
| 전원 | 1장(무엇을 만드는가), 2장(왜 이 구조인가), 3장(사용자 흐름), 12장(역할), 13장(로드맵) |
| AI / Data (3) | 6장(Persona), 7장(Ask), 8장(Act), 11장(검증 지표) |
| 기획 / 백엔드 (3) | 9장(DB), 10장(API), 11장(검증 설계·라벨링) |
| 프론트 (2) | 4장(화면 명세), 5장(리포트 설계) |
| 전원 | **11-3(라벨링 가이드)** — 6~8주차에 전원 투입된다 |

> ⚠️ 문서에 나오는 숫자(39%, 4.1/5 등)는 전부 UI 설명용 예시다. 실제 수치는 실행 후 교체한다.

## 1. 무엇을 만드는가

피그마 프로토타입을 올리면, **AI 사용자 100명과 실제 사용자 12~15명이 같은 과제를 수행**하고, 두 결과의 차이를 계산해 "이 AI 예측이 얼마나 틀리는지"를 함께 보여주는 웹 서비스.

### 1-1. 핵심 단위는 "테스트(내부 이름 Study)"

화면의 메뉴·버튼·설명·오류 문구는 사용자 요청에 따라 **테스트**로 통일한다. 이 문서의 스터디 및 코드·DB·API의 Study/studies는 같은 내부 개념이며 이름을 변경하지 않는다.

프로젝트나 실행 단위가 아니라 **스터디**를 중심에 둔다. 하나의 스터디는 다음을 포함한다.

```
Study
 ├─ 프로토타입    피그마 링크 (화면 + 연결 정보)
 ├─ 과제          "회원가입을 완료하세요"
 ├─ 문항          Q1~Q6 (AI와 실제 사람에게 동일하게 제시)
 └─ 참가자
      ├─ AI 패널       100명   (Ask 모드 + Act 모드)
      └─ 실제 참가자    12~15명 (Act만)
```

**참가자 유형이 다를 뿐 같은 스터디다.** 이것이 설계의 핵심이다. 실제 사용자 조사를 "나중에 하는 별도 실험"이 아니라 **스터디 안의 한 참가자 유형**으로 두면, 조건이 자동으로 동일해지고 비교가 제품 기능이 된다.

### 1-2. AI 패널이 하는 두 가지

같은 Persona 프로필로 두 번 돌린다.

| | Ask (묻는다) | Act (써보게 한다) |
| --- | --- | --- |
| 입력 | 제품 설명 + 기능 목록 + 가격 | 프로토타입 + 과제 |
| 하는 일 | 읽고 의향을 답한다 | 화면을 조작하고 계속할지 판단한다 |
| 출력 | 사용 의향, 기능 필요도, 우려 요인 | 과제 완료율, 이탈 화면, 이탈 이유 |
| 성격 | 말 | 행동 |
| 개발 | 1~4주차 | 5~6주차 |

P023이라는 동일한 가상 인물이 Ask에서는 "쓸 것 같다 4/5"라고 답하고 Act에서는 화면4에서 멈춘다. **같은 사람의 말과 행동이 어긋나는 것을 개인 단위로 추적할 수 있다.**

### 1-3. 최종 출력

```
Ask   (AI에게 물음)     "쓸 것 같다"      4.1 / 5
Act   (AI가 조작)       과제 완료율        39%
Real  (사람이 조작)     과제 완료율        52%
                                    ↓
                        오차: AI가 13%p 낙관적
                                    ↓
                   다음 스터디 결과에 이 오차를 병기
```

마지막 줄이 우리 제품의 차별점이다. 숫자를 주는 데서 끝내지 않고, **그 숫자의 오차를 함께 준다.**

### 1-4. 만들지 않는 것

- 실제 웹사이트·앱 자유 조작 — 피그마 프로토타입으로 한정. 확장 항목.
- 모델 학습·파인튜닝 — 공개 데이터 분포에서 표본 추출만 한다.
- 피그마 플러그인 — P2. MVP는 웹에서 링크를 받는다.
- 음성·화면 녹화 — 실제 참가자도 클릭 경로만 기록한다.
- 실제 구매 전환율 예측 — 상대적 순위만 다룬다.

## 2. 왜 이 구조인가

### 2-1. 참고한 것

이 분야에는 이미 앞선 서비스가 있다. 숨기지 않고 구조를 참고했다.

| 서비스 | 하는 일 |
| --- | --- |
| Versive (YC W23) | AI 모더레이션·정량/정성 문항·사용성 테스트를 하나의 스터디에서 결합. 실제 사용자, AI 페르소나, 또는 둘 다로 테스트. 피그마 플러그인 제공 |
| UserTesting | 2026년 1월 피그마 플러그인 출시. 프로토타입과 과제를 설명하면 테스트 스크립트를 자동 생성 |
| 인텔리시아 (국내) | 합성소비자에게 설문·인터뷰. 소비재 대기업 중심. 재현율 90% 이상 공개 |

**"하나의 스터디에 AI와 실제 사람을 함께 넣는다"는 구조는 Versive에서 가져왔다.** 우리가 발명한 것이 아니다. 피그마 공식 가이드도 합성 테스트로 구조적 문제를 잡고 이어서 소규모 실제 참가자 조사를 붙이는 혼합 방식을 권장한다.

### 2-2. 다르게 하는 것

혼합 방식 자체는 차별점이 아니다. 우리가 추가하는 것은 하나다.

> 기존 서비스는 AI 결과와 실제 사용자 결과를 **각각 보여준다.**
> 우리는 둘을 **대조해 오차를 계산하고, 그 오차를 다음 결과에 붙인다.**

```
기존:   AI 결과 리포트  +  실제 사용자 리포트   (두 벌의 데이터)

우리:   AI 결과  →  실제 결과와 대조  →  오차 산출
                                          ↓
              "이 유형 수치는 평균 13%p 낙관적입니다"
                                          ↓
                          다음 스터디 결과에 자동 병기
```

확인한 범위에서 개별 결과에 오차를 붙여 제시하는 서비스는 없다. 정확도 수치를 공개하는 곳은 있지만 그것을 결과 화면에 연결하지 않는다.

### 2-3. 그리고 한국 데이터

Versive를 포함한 해외 서비스의 페르소나는 한국 사용자를 전제로 하지 않는다. 우리는 통계청·건강보험공단 시드 기반 공개 데이터셋과 국내 조사 자료로 페르소나를 구성한다. 그리고 **그 페르소나가 한국 사용자에게 얼마나 맞는지를 실제 한국 대학생으로 측정한다.** 이 측정치는 확인된 범위에서 공개된 사례가 없다.

## 3. 사용자 흐름

프론트·백엔드 모두 이 흐름을 기준으로 작업한다. 우측 API는 10장 명세와 대응한다.

### ① 스터디 생성 — 10초

```
POST /studies  { name: "일정메이트 온보딩 테스트" }  → study_id
```

### ② 제품 정보 입력 — 1분

Ask 모드의 입력이 된다. 기획서에 있는 것을 붙여넣는다.

```
제품명   일정메이트
설명     일정을 자동 정리하고 우선순위를 추천
기능     자동 정리 / 우선순위 추천 / 캘린더 연동 /
         친구 공유 / 알림 설정
가격     무료 + 월 유료 전환

POST /studies/{id}/product  { description, features[], price }
```

### ③ 프로토타입 연결 — 30초

피그마 공유 링크를 붙여넣으면 화면과 버튼을 자동으로 읽어온다.

```
✓ 연결됨 — 화면 5개 인식

  S01  온보딩         [시작하기]
  S02  회원가입       [다음] [뒤로]
  S03  학교·학년      [다음] [건너뛰기]
  S04  관심분야 선택  [완료] [건너뛰기]
  S05  홈

POST /studies/{id}/prototype  { figma_url }
  → screens[], links[]
```

> ⚠️ 화면 간 연결이 설정된 프로토타입이어야 한다. 그림만 있는 파일은 동작하지 않는다. API 연동 실패에 대비해 수동 입력 폴백 UI를 함께 만든다.

### ④ 과제와 문항 확정 — 1분

**이 단계가 중요하다.** 여기서 확정한 과제와 문항이 AI와 실제 참가자 모두에게 동일하게 제시된다.

```
과제   회원가입을 완료하세요
목표   S05 (홈) 도달

문항   Q1 이 화면을 보고 무슨 앱인지 알겠는가        (1~5)
       Q2 가장 먼저 누를 것 같은 요소는              (선택)
       Q3 다음으로 넘어가겠는가, 그만두겠는가        (이분)
       Q4 그만둔다면 이유는                          (8개 카테고리)
       Q5 지금 쓰는 서비스에서 옮길 이유가 있는가    (1~5)
       Q6 유료로 쓴다면 월 얼마까지 낼 수 있는가     (금액 직접)

POST /studies/{id}/task, POST /studies/{id}/questions
```

### ⑤ AI 패널 생성 — 30초

개별 인물을 만드는 것이 아니라 **분포**를 고른다.

```
연령       20대
소속       대학생
앱 사용    중~높음
가격 민감  중~높음

POST /studies/{id}/panel/generate  → 100 personas
```

### ⑥ Ask 실행 — 2분

```
사용 의향     4.1 / 5
필요한 기능   자동 정리 61%   캘린더 22%
불필요        친구 공유 68%
우려          PRICE 34%   PRIVACY 19%

POST /studies/{id}/runs  { mode: "ask" }
```

### ⑦ Act 실행 — 5분

같은 100명이 프로토타입을 조작한다. 진행 중 로그가 실시간으로 흐른다.

```
P001  S01 →[시작하기]→ S02 →[다음]→ S03 → 이탈
P002  S01 →[시작하기]→ S02 →[다음]→ S03
      →[건너뛰기]→ S04 →[완료]→ S05  ✓ 완료

POST /studies/{id}/runs  { mode: "act" }
GET  /runs/{id}/status
```

### ⑧ 실제 참가자 초대 — 링크 배포

같은 스터디에 참가자 유형만 다르게 추가한다. 링크를 받은 사람은 동일한 프로토타입으로 동일한 과제를 수행한다.

```
POST /studies/{id}/invites  { count: 15 }
  → 참가 링크 생성

참가자 화면:
  1. 과제 안내
  2. 프로토타입 (임베드)
  3. 이탈 시 이유 선택 (AI와 동일한 8개 카테고리)
  4. Q5, Q6 응답
```

> 참가자 화면은 AI와 조건이 완전히 같아야 한다. 안내 문구, 과제 문장, 이탈 이유 선택지가 한 글자라도 다르면 비교가 성립하지 않는다.

### ⑨ 결과 확인

```
┌─ 퍼널 ────────────────┐   ┌─ 이탈 이유 ───────────┐
│  S01  AI 100 / 실 15  │   │  TOO_MANY_STEPS  41%  │
│  S02  AI  88 / 실 13  │   │  PRIVACY         28%  │
│  S03  AI  71 / 실  9  │   │  UNCLEAR_PURPOSE 16%  │
│  S04  AI  44 / 실  6  │ ← │                       │
│  완료 AI  39 / 실  8  │   └───────────────────────┘
└───────────────────────┘

┌─ 말 vs 행동 ─────────────────────────────┐
│  Ask  "쓰겠다"  4.1 / 5                   │
│  Act  완료율    39%                       │
│  ⚠ 쓰겠다고 답한 76명 중 37명이 못 끝냄   │
└───────────────────────────────────────────┘

┌─ 신뢰도 ─────────────────────────────────┐
│  이탈 화면 순위   AI = 실제  ✓ 일치       │
│  완료율          AI 39% / 실 52%          │
│                  → AI가 13%p 낙관적       │
└───────────────────────────────────────────┘
```

### ⑩ 개별 추적

```
P023   23세 / 가격민감 0.76

  Ask   "쓸 것 같다" 4/5
        "자동 정리가 유용해 보인다"

  Act   S01 통과 → S02 통과 → S03 통과
        → S04 이탈  (TOO_MANY_STEPS)
        "관심분야까지 고르라니 그만두겠다"
```

### ⑪ 수정 후 재실행

```
수정    관심분야 선택 → 가입 후로 이동
재실행  Act 완료율 39% → 67%
```

AI만 5분이면 재실행된다. 실제 참가자는 다시 모으지 않는다. **이것이 혼합 구조의 실질적 이점이다.** 실제 참가자는 오차를 재는 데 한 번 쓰고, 이후 반복은 AI로 하되 그 오차를 붙여서 읽는다.

| Invite | 실제 참가자 링크 생성·현황 | `POST .../invites` | P0 |
| **참가자 뷰** | 과제 안내 → 프로토타입 임베드 → 이탈 이유 | `POST /participate/...` | P0 |
| Report | 퍼널(AI/실제 중첩), 이탈 이유, 말vs행동, 신뢰도 | `GET /studies/{id}/report` | P0 |
| Explorer | 개별 Persona의 Ask 응답 + Act 경로 | `GET /personas/{id}` | P1 |

> 참가자 뷰를 P0에 둔 이유: 이 화면이 없으면 실제 사용자 데이터를 수집할 방법이 없고, 그러면 오차 계산이 불가능해진다. 우리 제품의 차별점이 통째로 사라진다.

**스텝 네비게이션을 고정한다.** 이전 단계 미완료 시 다음 버튼을 비활성화한다.

```
③ 공개 조사 자료에서 경제 변수 결합
④ 타깃 조건으로 모집단 분포 제한
⑤ 분포에서 100개 표본 추출
⑥ 생성 직후 분포 점검 — 특정 값 쏠림 시 경고
```

### 6-3. Persona Schema

```json
{
  "persona_id": "P023",
  "age": 23,
  "occupation": "university_student",
  "app_usage_freq": 0.82,
```

## 8. Act 모드 — Agent Loop (AI/Data, 핵심)

### 8-1. 피그마에서 가져오는 것

```
screens = [
  { id: "S01", label: "온보딩",
    elements: [{ text: "시작하기", to: "S02" }] },
  { id: "S02", label: "회원가입",
    elements: [{ text: "다음", to: "S03" },
               { text: "뒤로", to: "S01" }] },
  ...
]
```

연결 정보가 구조화되어 있으므로 에이전트는 **정해진 선택지 중 고르는 문제**만 푼다. 브라우저를 직접 조작하거나 화면을 해석할 필요가 없다.

### 8-2. 루프 의사코드

```python
for persona in personas:                    # 100명
    current = START_SCREEN
    visited = []
    for turn in range(MAX_TURNS):           # 상한 필수
        obs  = build_observation(current)   # 화면 + 클릭 가능 요소
        resp = llm(persona, task, obs, schema)
        log(persona, turn, current, resp)

        if not resp.continue:
            record_drop(persona, current, resp.drop_reason)
            break
        if resp.target not in obs.elements: # 목록 밖 응답
            retry(); continue

        current = next_screen(current, resp.target)
        if current == GOAL_SCREEN:
            record_complete(persona); break
        if current in visited:              # 같은 화면 반복
            record_drop(persona, current, "NAVIGATION_LOST"); break
        visited.append(current)
    else:
        record_drop(persona, current, "MAX_TURNS")
```

> ⚠️ **`MAX_TURNS` 상한과 `visited` 중복 차단을 5주차에 가장 먼저 구현한다.** 없으면 에이전트가 두 화면을 무한히 오가며 API 비용을 태운다.

### 8-3. 프롬프트 구조

```
System   너는 앱을 처음 써보는 사용자다. 주어진 프로필의 사람으로서
         행동한다. 클릭 가능한 요소 목록에 없는 것은 선택할 수 없다.
         계속할 수 없다고 판단되면 그만둔다고 답한다.
Persona  {persona_json}
Task     회원가입을 완료하세요
Screen   현재 화면: 학교·학년 입력
         화면 설명: 학교명, 학년, 전공을 입력받는 폼
         클릭 가능: [다음] [건너뛰기]
History  지금까지: 온보딩 → 회원가입 → (현재)
Schema   {출력 JSON 스키마}
```

### 8-4. 출력 스키마

```json
// 계속하는 경우
{ "action": "click", "target": "다음",
  "continue": true, "reason": "가입은 해보겠다" }

// 이탈하는 경우
{ "action": "abandon", "target": null,
  "continue": false, "drop_reason": "TOO_MANY_STEPS",
  "reason": "학교와 관심분야까지 요구해 부담된다." }
```

### 8-5. 고정 카테고리

| 코드 | 의미 |
| --- | --- |
| `UNCLEAR_PURPOSE` | 무슨 앱인지 모르겠다 |
| `TOO_MANY_STEPS` | 단계·입력 항목이 너무 많다 |
| `PRIVACY` | 개인정보를 과하게 요구한다 |
| `PRICE` | 가격이 부담된다 |
| `TRUST` | 믿기 어렵다 |
| `FEATURE_MISSING` | 필요한 기능이 없다 |
| `SWITCHING_COST` | 쓰던 것을 옮기기 번거롭다 |
| `NAVIGATION_LOST` | 어디로 가야 할지 모르겠다 |

> ⚠️ 이 체계는 **① AI 이탈 이유, ② 실제 참가자 이탈 이유, ③ 앱 리뷰 라벨링** 세 곳에서 동일하게 쓴다. 하나라도 다르면 비교가 성립하지 않는다. **6주차까지만 변경 가능, 이후 동결.**

### 8-6. 비용 관리

| 항목 | 추정 | 대응 |
| --- | --- | --- |
| Ask | 100명 × 1회 = 100 호출 | — |

## 9. DB Schema (백엔드)

### 이메일 로그인 추가 (2026-11-02 사용자 요청)

실제 로그인 요청에 따라 기존 users·스터디·결과 스키마를 유지하고 인증 전용 user_credentials(user_id, password_hash)와 auth_sessions(token_hash, user_id, expires_at, created_at)을 추가한다. 비밀번호는 Argon2id 해시만 저장하고 세션은 무작위 토큰의 SHA-256 해시만 DB에 저장한다. 기존 개발 사용자 자동 입장은 제거한다. HttpOnly 쿠키, CSRF 요청 헤더와 허용 Origin 검사, 로그인 시도 제한을 적용한다. /auth/register, /auth/login, /auth/me, /auth/logout으로 이메일 가입·로그인·세션 확인·로그아웃을 제공한다. 이메일 확인/복구 메일 및 소셜 로그인은 메일/OAuth 서비스 설정 전에는 제공하지 않는다. 기존 개발 계정의 스터디를 새 계정으로 자동 이전하지 않는다.

| Table | 주요 컬럼 | 비고 |
| --- | --- | --- |
| `users` | id, email, created_at | |
| `studies` | id, user_id, name, status | **핵심 단위** |
| `products` | id, study_id, description, features_json, price | Ask 입력 |
| `prototypes` | id, study_id, figma_url, screens_json, links_json | Act 입력 |
| `tasks` | id, study_id, description, goal_screen_id | 과제 |
| `questions` | id, study_id, code, type, text | AI·실제 공용 |
| `personas` | id, study_id, attributes_json | AI 패널 |
| `runs` | id, study_id, mode(ask\|act), status, progress | 실행 관리 |
| `ask_responses` | id, run_id, persona_id, response_json | Ask 응답 |
| `act_logs` | id, run_id, **participant_type(ai\|real)**, participant_id, turn, screen_id, action, target, drop_reason, reason | **AI와 실제가 같은 테이블** |
| `invites` | id, study_id, token, status, opened_at | 참가자 링크 |

`calibrations`에 쌓인 오차가 이후 스터디의 신뢰도 블록에 표시된다.

## 11. 검증 설계 (전원 참여)

이 장이 프로젝트의 핵심 주장을 뒷받침한다. 코드보다 이 작업이 결과물의 질을 결정한다.

### 11-1. 사전 검증 — 기출시 앱 대조 (5~9주차)

사람을 모으지 않고 반복할 수 있어, 여기서 프롬프트와 카테고리를 다듬는다.

```
① 대학생 이용 비중이 높은 국내 출시 앱 20개 선정
② 각 앱의 출시 시점 제품 설명·기능 목록만 입력 (출시 후 정보 차단)
③ Ask 모드로 우려 요인 예측
④ 실제 리뷰를 고정 카테고리로 라벨링해 실측 기준 생성
⑤ 예측 순위와 실측 순위 대조
⑥ 보정용 10개로만 보정, 평가용 10개로 성능 측정
```

> ⚠️ 보정용과 평가용을 반드시 분리한다. 보정에 쓴 앱으로 성능을 재면 수치가 부풀려진다. `benchmark_apps.group` 컬럼으로 강제한다.

**한계 인식:** 앱스토어 리뷰는 이탈하지 않고 남은 사용자가 쓴 것이다. 따라서 사전 검증은 이탈 지점이 아니라 **불만 요인의 종류와 순위**만 평가한다. 이탈 지점의 일치는 본 검증에서 확인한다.

### 11-2. 본 검증 — 같은 스터디 안의 실제 참가자 (9~10주차)

**별도 실험이 아니다.** 스터디에 참가자 유형을 하나 더 추가하는 것이다.

| 항목 | 내용 |
| --- | --- |
| 참가자 | 20대 대학생 12~15명 |
| 제시물 | AI와 **동일한** 프로토타입 (같은 study_id) |
| 과제 | AI와 **동일한** 문장 |
| 이탈 이유 | AI와 **동일한** 8개 카테고리 |
| 기록 | `act_logs`에 `participant_type: "real"`로 저장 |
| 소요 | 1인당 10~15분 |

조건이 자동으로 같아진다. 스터디 구조가 그것을 강제하기 때문이다.

**참가자 12~15명인 이유:** 응답 비율을 통계적으로 비교하려면 30명 이상이 필요하다. 그러나 우리가 확인하는 것은 비율이 아니라 **순위**다. "가장 많이 막히는 화면이 어디인가"에는 이 규모로 충분하며, 사용성 테스트에서 주요 문제 발견에 필요한 표본이 통상 이 수준으로 알려져 있다. 모집 실패 위험도 크게 낮아진다.

**모집:** 학과·동아리·교내 커뮤니티. 8주차 착수, 9주차 시작 시 확보 확인. 미달 시 사전 검증을 주 근거로 전환.

### 11-3. 리뷰 라벨링 가이드

6~8주차에 전원이 참여한다. 기준이 제각각이면 작업 전체가 무의미해진다.

- 리뷰 1건당 카테고리 **1개만** 선택한다. 여러 불만이 섞였으면 가장 강하게 표현된 것 하나.
- **별점 3점 이하** 리뷰만 라벨링한다.
- 앱당 **최근 리뷰 100건**. 100건 미만이면 전량.
- 해당 없으면 `OTHER`로 두고 억지로 배정하지 않는다.
- **시작 전 10건을 5명이 동시에 라벨링해 일치도를 확인한다. 70% 미만이면 기준을 다시 맞춘 뒤 본작업.**
- 라벨러 ID를 기록한다 (`benchmark_issues.labeler_id`).

### 11-4. 지표 정의

| 지표 | 계산식 | 구분 |
| --- | --- | --- |
| 의향-행동 격차 | (Ask 긍정 비율) − (Act 완료율) | 핵심 |
| 이탈 화면 일치 | Act 최다 이탈 화면 = Real 최다 이탈 화면 | 대표 |
| 이탈 이유 일치 | 상위 3개 카테고리 교집합 ÷ 3 | 대표 |
| 퍼널 방향 일치 | 화면별 잔존율 감소 순서의 순위 상관계수 | 대표 |
| 앵커 수렴률 | 제시 금액과 동일하게 답한 비율 | 편향 감시 |
| 행동 다양성 | Persona 간 이탈 화면 분산 ÷ Real 분산 | 편향 감시 |
| 완료율 차이 | \|Act 완료율 − Real 완료율\| | 참고 |

**대표 지표를 순위로 잡은 이유:** 합성 응답이 절대 수치를 맞히기 어렵다는 것은 이미 알려진 사실이다. 완료율 차이를 대표로 내세우면 "39%와 52%의 차이가 좋은 것인가"에 답할 근거가 없다. 어느 화면에서 막히는지, 왜 막히는지를 맞히는가를 기준으로 삼는다.

### 11-5. 결과가 반대로 나올 경우

실제 참가자가 Act가 아니라 Ask에 가깝게 나올 수 있다. 그 경우에도 **결과를 그대로 기록한다.** 조작 방식이 기대만큼 정확하지 않다는 것 역시 측정된 사실이며, 어떤 조건에서 그런지를 함께 기술한다.

이 가능성을 문서에 미리 적어두는 이유는, 그래야 원하는 결과가 나왔을 때 그 결과를 믿을 수 있기 때문이다.

## 2026-11-02 기존 생성 패널의 DB 가져오기 명세

사용자 요청에 따라 feat/ux-eval의 df031741730d4f4ef84c9146e2c8f88bd768fa94 커밋에서 검증된 패널 4개(각 100명)를 가져온다. 기존 테스트에 속한 personas를 공용 보관함으로 재사용하지 않고 아래 두 테이블을 추가한다. 기존 9장의 테이블, 이탈 코드, 실행 종료 조건은 변경하지 않는다.

- persona_library_panels: id(Integer PK), panel_key(String 200), version_hash(String 64), source_commit(String 40), metadata_json(JSONB), created_at(timestamptz). UNIQUE(panel_key, version_hash).
- persona_library_entries: id(Integer PK), panel_id(FK persona_library_panels.id, ON DELETE RESTRICT), source_persona_id(String 50), profile_hash(String 64), attributes_json(JSONB). UNIQUE(panel_id, source_persona_id).
- 패널 버전은 원본 Parquet와 보고서의 SHA-256으로 고정한다. 같은 파일을 재가져오면 기존 패널을 검증하고 재사용한다. 내용이 바뀌면 새 버전을 추가하고 기존 버전을 덮어쓰지 않는다.
