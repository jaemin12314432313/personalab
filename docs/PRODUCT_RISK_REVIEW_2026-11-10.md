# PersonaLab 현재 앱 문제 진단

검토일: 2026-11-10  
범위: 현재 로컬 코드·기획 문서·자체 작성 입력으로 확인한 리포트 함수. 실제 고객 데이터·원본 페르소나 전송·유료 LLM 호출 없음. 현재 앱의 모든 화면을 육안 검수하거나 모든 사이트에서 실행한 결과는 아니다.

## 핵심 판단

**한 번 탐색을 실행하고 기록을 보여주는 기반은 있다. 그러나 한 앱을 반복해서 검토하고, 그 결과로 UI·UX 수정 결정을 믿고 내리는 제품이 되려면 ‘검토의 타당성 → 관찰의 정확성 → 결과의 완전성 → 조건을 보존한 반복’이 더 필요하다.**

가장 큰 위험은 기능이 적은 것보다 **제한된 관찰이 충분한 검토처럼 보이는 것**이다. 예쁜 얼굴·여러 명·움직이는 화면·자연스러운 인터뷰가 그 한계를 가릴 수 있다.

### 이미 있는 것을 없는 문제로 다시 지적하지 않는다

- 실제 이메일 인증 흐름과 쿠키 세션, 계정 소유권 검사가 있다. 운영 계정 복구·정책 완성과는 별개다.
- 브라우저의 실제 캡처와 요소가 LLM 입력에 들어간다. 현재 엔진을 텍스트만 읽는 가짜 실행이라고 볼 수 없다.
- `product_id`와 `test_title`로 같은 앱의 테스트를 묶고, 기존 앱 선택·주소/대상 상속을 지원하는 코드가 있다.
- 브라우저 실행은 설정된 동시 인원으로 돌릴 수 있고, 개별 일시 실패가 다른 사람을 무조건 중단시키지 않도록 개선돼 있다.
- LLM 탐색의 동일 화면 재방문은 제한 범위에서 허용한다. 예전의 즉시 재방문 차단만 있다고 지적하면 틀린 진단이다.
- 실행 종료·부분 결과·인터뷰 접근 조건과 캡처 디코드 동기화가 있다. 개선 여부를 그 위에서 평가해야 한다.

아래에서는 **확인**(코드의 현재 동작/제약), **위험**(현재 구조에서 발생할 수 있는 제품·방법론 문제), **미검증**(필요한 품질 증거를 이번 검토에서 확인하지 못함)을 구분한다. 미검증은 실패를 확정한 것이 아니다.

우선순위: **P0** 잘못된 결과/해석을 막는 핵심, **P1** 실제 고객 사용·반복을 막는 부분, **P2** 확장과 유지보수 단계. 앱·DB·종료 규칙을 이번 진단으로 변경하지 않는다.

## 1. 직접 재현한 세 가지

현재 소스의 `analyzeReport`, `recordAnswer`, `comparisonMarkup`을 Vite SSR로 불러와 자체 작성한 작은 입력으로 검사했다. 원본 카드 0개, 외부 모델 호출 0회. Vite HMR 포트 경고가 있었으나 함수 검사는 완료됐다.

| 입력 | 실제 결과 | 의미 |
| --- | --- | --- |
| 중간에 필터 위치가 불명확했다는 행동 이유가 있지만 마지막 결과는 목표 도달 | 핵심 발견 수 0 | 핵심 발견이 중단 중심이라 성공 경로의 불편을 놓침 |
| 마지막 행동 stop, 종료 이유 NAVIGATION_LOST인 시스템 종료에 ‘왜 멈췄나요?’ 질문 | 프론트 기록 답변에 MAX_TURNS가 근거로 나옴 | 종료 분류를 새로 고친 뒤 답변 문구가 맞춰지지 않음 |
| 비교 전 시스템 종료 0건, 비교 후 1건 | ‘탐색 마침·한도’ 증가에 `good` 클래스 적용 | 시스템 종료 증가는 UX 개선 근거가 아닌데 긍정적 변화로 표시 |

첫 사례는 엔진이 못 보는 것이 아니라 **결과 집계 방식의 한계**다. 뒤의 두 사례는 현재 코드의 구체적인 불일치다. 세 함수 수준 검사이며 실제 화면을 클릭해 재현한 검사는 아니다.

## 2. 제품·테스트·반복 사용

| 번호 | 상태·우선 | 문제와 영향 | 해결 방향·확인 기준 |
| --- | --- | --- | --- |
| R01 | 확인·P1 | 제품 묶음은 생겼지만 공통 제품 정보가 각 테스트의 scope와 입력에 흩어져 있다. 하나의 앱 정보와 어떤 테스트의 정보를 기준으로 하는지 불분명해질 수 있다. | 명시적 소속은 유지하고 제품 공통값·테스트별 예외·실행 당시 값을 구분. 서로 다른 두 테스트를 다른 기기에서 열어 일관성 확인. [E1] |
| R02 | 확인·P1 | 기존 앱 상속은 주소·뷰포트·유형·대상·설명을 중심으로 한다. HTML 파일 묶음·수집 화면을 제품 자료로 직접 재사용하는 경험과는 다르다. | 입력 종류별 재사용 계약 필요. 같은 HTML 앱의 두 테스트를 원본 재업로드 없이 만들 수 있는지 검증. [E1] |
| R03 | 확인·P0 | 제품 ID·테스트 제목·회차 메모는 있으나 앱의 화면 버전과 실행 회차를 독립 관리하는 계약이 충분하지 않다. ‘3회차’가 어떤 배포 화면인지 보장하지 못한다. | 자료 식별·관찰 시각·버전 이름·기기 조건을 결과에 고정. 같은 URL이 바뀐 두 회차를 구별. DB 변경은 별도 명세 검토. [E1] |
| R04 | 확인·P1 | 제품의 대표 이름과 상속 출처를 모은 목록의 첫 테스트에서 가져온다. 같은 앱의 테스트마다 설명·대상이 다르면 어느 값이 공통인지 흔들릴 수 있다. | 대표 출처를 명시하고 특정 테스트 설정을 공통값으로 오인시키지 않기. 순서가 바뀌어도 제안 기본값이 설명 가능해야 함. [E1] |
| R05 | 확인·P1 | 현재 작업이 running이면 새 테스트 생성 자체를 막는 프론트 경로가 있다. 한 앱의 실행을 기다리며 다음 검토를 준비하기 어렵다. | 실행 추가와 초안 작성·다른 테스트 열기를 구분. 데이터 덮어쓰기 없이 실행 중 다음 초안을 저장할 수 있는지 확인. [E1] |
| R06 | 확인·P1 | 제품 소속·테스트 제목을 서버에 저장하는 일부 경로에서 실패를 catch하고 이후 단계에서 다시 저장하도록 한다. 사용자는 소속까지 저장된 것으로 생각할 수 있다. | 서버 저장 완료와 로컬 초안을 구분하고 재시도/실패를 보이기. 해당 저장만 실패시켜 다른 PC에서 소속이 사라지는지 검증. [E1] |
| R07 | 위험·P1 | 제품 홈에서 ‘결과가 있음’과 ‘현재 화면 버전에서 검토함’을 같은 상태로 읽을 수 있다. 예전 결과만 보고 이번 변경까지 검토했다고 믿게 된다. | 테스트별 마지막 검토 자료와 현재 자료를 대조. 버전 미검토·실행 중·부분 결과를 별도 표시. 앱 전체 검증률로 환산하지 않기. [E1] |

핵심: **같은 이름으로 묶는 기능과, 한 제품의 검토 이력을 신뢰할 수 있게 관리하는 기능은 완성 조건이 다르다.** 현재 추가된 소속 기능을 출발점으로 삼아야 한다.

## 3. 연결과 실제 웹 조작의 한계

| 번호 | 상태·우선 | 문제와 영향 | 해결 방향·확인 기준 |
| --- | --- | --- | --- |
| R08 | 확인·P1 | GET/HEAD 외 요청을 차단한다. 읽기 작업도 POST를 쓰는 GraphQL·검색·폼 기반 서비스에서는 화면의 핵심 기능이 막힐 수 있다. | 보호를 무조건 해제하지 말고 읽기 요청까지 필요한 지원 환경을 구분. 샌드박스/모의 API·허용 정책을 따로 설계. [E2] |
| R09 | 확인·P1 | 다른 출처 이동·팝업·WebSocket·서비스 워커가 제한된다. 로그인·새 창 상세·실시간 기능 등 정상 앱 흐름도 지원 밖일 수 있다. | 입력 단계에서 지원 범위 진단, 실행 종료에서는 환경 제한과 UX 이탈 구분. 기능별 호환 테스트 필요. [E2] |
| R10 | 확인·P1 | 요소 추출은 주 문서 querySelectorAll 중심이다. iframe 내부·shadow DOM·canvas의 좌표형 UI를 같은 방식으로 다룰 수 없다. | 입력 종류별 불가 영역 표시, 지원할 경우 별도 관찰/조작 경로. 이미지에 보이는 것과 실제로 누를 수 있는 것을 구분. [E2] |
| R11 | 확인·P1 | 기본 관찰은 요소 60개·본문 6000자 한도와 순위 규칙을 쓴다. 복잡한 화면의 일부가 행동 후보에서 빠질 수 있다. | 단순히 무제한 증가시키지 말고 현재 영역/대화상자/섹션별 관찰. 한도에 따른 미확인 범위를 기록. [E2] |
| R12 | 확인·P0 | DOM 후보에는 화면 밖 요소도 포함될 수 있고 locator 클릭은 자동 스크롤할 수 있다. 실제 사람은 발견하기 어려운 버튼을 에이전트가 이름으로 바로 고를 수 있다. | 실사용 탐색과 구조 점검의 모드 구분. 현재 화면에서 보이는 후보·노출 과정·자동 스크롤을 기록하고 발견성을 과장하지 않기. [E2] |
| R13 | 확인·P1 | 지원 행동은 클릭·채우기·아래 스크롤 중심이다. 위 스크롤·브라우저 뒤로·키보드 조작·hover·드래그가 일반 행동으로 준비되지 않았다. | 실제 지원 행동 표를 만들고 필요한 행동부터 확장. 지원하지 않는 조작을 해당 제품의 UX 문제로 분류하지 않기. [E2] |
| R14 | 위험·P1 | 상태 ID가 본문·요소·스크롤에 의존한다. 시계·배너·동적 문구만 바뀌어 다른 상태가 되거나 같은 업무 상태가 잘게 쪼개질 수 있다. | 화면 정체성과 일시적 상태를 분리하는 정규화. 시간만 바뀌는 화면·탭 전환·스크롤을 각각 시험. MAX_TURNS 보호는 유지. [E2] |

‘네이버라 복잡해서 그렇다’만으로 설명할 수 없다. 보통의 SaaS도 API·동적 상태·인증·별도 창을 많이 쓴다. **지원 범위를 명확히 정하고 그 범위 안의 성공률을 높이는 작업**이 필요하다.

## 4. 페르소나가 실제로 기여하는가

| 번호 | 상태·우선 | 문제와 영향 | 해결 방향·확인 기준 |
| --- | --- | --- | --- |
| R15 | 미검증·P0 | 카드의 차이가 재현 가능한 행동 차이·문제 발견의 추가 가치로 이어지는지 이번 검토에서 검증 자료를 확인하지 못했다. | 같은 화면·과제에서 카드 변경/미사용 기준선을 반복 비교. 말투가 아닌 경로·실제 근거·발견 품질을 평가. |
| R16 | 확인·P1 | 구성 추천은 명시 필터로 추린 후 다양성을 높이는 방식이다. 자유 서술한 대상 설명을 의미적으로 이해해 적합한 직무 경험을 찾는 추천은 아니다. | 추천의 의미를 정확히 안내. 의미 매칭을 넣는다면 실제 보유 특성에 근거하고 적합도 검증. [E3] |
| R17 | 위험·P1 | 나이·직무·친숙도의 다양성이 제품 관련성을 대신할 수 있다. 다양한 구성이 곧 이번 앱의 적합한 사용자 구성은 아니다. | 필수 적합 조건과 선택 다양성 조건을 분리. 없는 경험은 만들어 채우지 않기. [E3] |
| R18 | 위험·P0 | 여러 카드가 같은 계열 모델·프롬프트를 사용한다. 20명 출력이 실제 독립 사용자 20명의 증거가 되는 것은 아니다. | 영향 인원은 ‘이번 AI 구성의 기록’으로 표기. 실제 고객 비율/통계적 대표성 주장 금지. 모델의 공통 편향·중복 행동 측정. [E2][E10] |
| R19 | 위험·P1 | 에이전트에게 준 제품 소개·과제가 화면보다 더 많은 정보를 줄 수 있다. 화면만으로 이해하는지를 보려는데 설명으로 답을 알려줄 수 있다. | 배경 문맥과 화면에서 알아야 할 정보를 구분. 첫 화면 이해 검토에서는 사전 정보량을 통제. [E4] |
| R20 | 확인·P1 | 전반 탐색은 사람별 미방문 페이지를 시작점으로 배정할 수 있다. 다른 사람의 다른 행동이 프로필 때문인지 출발 화면 때문인지 섞인다. | 공통 시작 비교와 범위 분산 탐색을 구분. 배정된 시작점·맥락을 결과에 유지. 직접 URL 진입을 발견 성공으로 세지 않기. [E4] |
| R21 | 위험·P1 | 실사형 얼굴이 행동 모델의 검증 수준보다 큰 신뢰를 만들 수 있다. 얼굴과 프로필이 실제 조사 참여자처럼 읽힐 수 있다. | AI 대표 이미지·재사용 여부를 명확히 하고 신뢰의 중심을 화면/행동 근거에 두기. 고객 이해도 확인. |

핵심 연구 질문은 “페르소나가 자연스럽게 말하나?”가 아니다. **“같은 화면을 일반적인 AI 한 번에 검토하는 것보다 무엇을 더 유용하게 찾는가?”**다.

## 10. 서로 엮여 더 위험해지는 문제

### 가짜로 좋은 결과가 나오는 경로

DOM에서 화면 밖 버튼까지 알 수 있음(R12) → 안내를 놓치지 않고 바로 클릭 → 목표 도달 → 중간 불편은 핵심 발견에서 제외(R29) → ‘문제 없음’처럼 읽음(R34).

### 고치지 않았는데 좋아진 것처럼 보이는 경로

다른 화면·다른 시작점·모델/문맥 변화(R20·R39·R40) → 문제 화면 방문 인원 감소(R42) → 핵심 발견 감소 → 비교에서 개선처럼 해석(R37·R41).

### 내용이 부족해도 믿게 되는 경로

실사 얼굴(R21) → 실제 캡처가 움직이는 3D → 그럴듯한 이유 → 유효한 로그 ID만 인용(R43) → 후속 인터뷰의 새 해석을 실제 원인으로 믿음(R48).

### 반복 사용할수록 어려워지는 경로

제품 정보 분산(R01) → 어떤 자료가 공통인지 흔들림(R04) → 화면 버전 불명확(R03) → 현재 검토 여부가 모호(R07) → 잘못된 회차 비교.

## 12. 유용성을 확인할 최소 평가 설계

### 네 비교 조건

1. 일반적인 AI에게 같은 UI를 한 번 검토하게 한 결과.
2. 동일 자료·행동 조건에서 페르소나 카드만 달리한 결과.
3. 수정하지 않은 화면을 같은 조건으로 여러 번 실행한 결과.
4. 실제 사람이 같은 화면을 사용하며 남긴 관찰 또는 검증 가능한 문제 정답 묶음.

하나의 실행 결과를 정답으로 삼지 않는다. 처음에는 적은 대표 화면/흐름에서 시작하고 필요한 표본·반복 횟수는 파일럿 변동을 본 뒤 정한다.

### 평가할 것

- 실제 화면에서 재현 가능한 문제를 얼마나 찾았는가.
- 정상 화면을 잘못 지적한 비율과 중요한 문제를 놓친 정도.
- 페르소나가 일반 AI 기준선보다 추가한 유용한 발견과 불필요한 중복.
- 수정 없는 반복의 흔들림과 실제 수정 후 변화의 구분.
- 각 주장에 연결한 화면·행동 근거의 정확성.
- 실제 조작 실패·환경 제한을 UX 문제와 분리한 정도.
- 고객이 리포트를 읽고 수정할 일을 정하는 데 필요한 노력.
- 한 검토의 실제 지연·모델 호출·재시도·저장 크기.

고객이 돈을 내는 근거는 인물 사진 수나 채팅 길이가 아니라 **수정할 지점을 더 빨리, 근거 있게 찾게 해주는가**여야 한다.

## 14. 외부 연구를 해석하는 범위

[Playwright 공식 Actions 문서](https://playwright.dev/docs/input#mouse-click)는 locator 클릭이 요소를 화면 안으로 스크롤하는 동작을 설명한다. R12는 이 자동화 특성과 우리 후보 추출 방식을 함께 고려한 진단이다. 자동 클릭 자체가 잘못이라는 뜻은 아니며 사람의 발견성 평가와 구분해야 한다.

[Hämäläinen 외, CHI 2023](https://acris.aalto.fi/ws/portalfiles/portal/106452436/SCI_H_m_l_inen_etal_CHI_2023.pdf)은 합성 HCI 데이터의 활용 가능성과 품질 검증 필요성을 다룬다. 이 연구로 현재 모델의 브라우저 UX 성능을 단정하지 않는다.

[Kapania 외, CHI 2025, Simulacrum of Stories](https://www.shivanikapania.com/assets/chi2025paper1.pdf)는 정성 연구자 19명을 대상으로 합성 인터뷰 참가자의 한계를 조사했다. 자연스러운 서사와 맥락 깊이/실제 경험의 차이를 제기한다. 브라우저 에이전트의 조작 정확도를 측정한 논문은 아니다. PersonaLab에서는 **인터뷰가 그럴듯하다는 이유로 관찰 타당성까지 보장하지 말아야 한다**는 제한된 교훈으로 적용한다.

이 앱의 유용성은 결국 우리 자료·과제·모델·고객 환경에서 직접 평가해야 한다.
